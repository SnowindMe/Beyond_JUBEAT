### 2.2 根因一：曲目库每请求渲染 1683 张卡（P0）

- `src/pages/songs.astro`：`export const prerender = false`（全站唯一运行时页），`getAllSongs()` 走 D1（isolate 缓存 60s），模板一次吐出 1683 个 `<article>`。
- CPU 剖面（Profiler 采样率 400µs，冷缓存）：总采样 24639ms，**主线程忙时 3223ms**；DOM 24944 节点。
- 该页已设 `cache-control: public, max-age=30, s-maxage=300, stale-while-revalidate=60`，边缘命中时不打 Worker；问题出在**回源那一下**：多个用户/多个标签页同时 miss 时，每个 miss 都要跑一遍完整渲染。
- **可复现的线上故障**：并发 5 起 → 503 `error code: 1102`（Worker 超出资源配额）。单个请求多数成功，所以平时不易察觉；一旦被分享/被爬虫/被多标签同时打开就出现。
- 修复方向（按性价比排序）：
  1. **把渲染结果搬出 Worker**：构建期把曲目数据固化成一个静态 JSON（`/api/songs.json`，immutable + 内容哈希），页面壳静态化，列表在客户端首屏后填充；同时保留无 JS 的降级块。
  2. **边缘缓存拉长 + 主动预热**：`s-maxage` 300 → 3600，构建完成后由 CI 打一次预热请求；配合 `Cache-Status` 观测命中率。
  3. **降低单次渲染成本**：首屏只渲染前 N 个世代块，其余用 `content-visibility` + 客户端 `IntersectionObserver` 补（现在虽然有 `content-visibility: auto`，但 DOM 仍要建满 24944 个节点）。
  4. 若保持 SSR，至少把 `getAllSongs` 的结果放进 KV/Cache API（跨 isolate），并把卡片 HTML 片段缓存复用。

### 2.3 根因二：字体与首屏文本绘制（P1）

- 每页两个字体：`jost-latin-500-normal.woff2`（10.8KB）、`montserrat-latin-500-normal.woff2`（19.0KB），都来自 `cdn.jsdmirror.com`；montserrat 是正文/UI 字族，通过 CSS `@font-face` 引入，**首屏文本要等它到达才能定稿**（FOIT/回流），首页 FCP 落在 2.1–3.5s 与字体到达时间强相关。
- 建议：①字体自托管到同源（子集化后 montserrat 500 约 8–10KB）；②同源后加 `<link rel=preload as=font crossorigin>`；③或直接 `font-display: swap` + 本地系统字体栈兜底，把第三方域从关键路径上摘掉。
- 附带收益：去掉一个外部域 = 少一次 DNS+TLS，登录/注册页的 Turnstile 域名才真正成为唯一的第三方关键路径。

### 2.4 根因三：曲目库移动端 CLS（P1）

- 移动端 CLS 0.030–0.035（桌面 0.015–0.03）。卡片图 `<img>` 有 width/height，但图在 3 列网格里按容器缩放，筛选/切服后网格重算高度，触发二次位移。
- 建议：给 `.sc-media` 用 `aspect-ratio: 1/1` 锁死盒子；统一 `contain-intrinsic-size` 的估算与实际卡高一致（现有 `refreshIntrinsicNow` 已是这套思路，缺的是移动端首帧的估值）。

### 2.5 体量与第三方（P2）

- 静态资源：bg 604KB（最大 jubeat.webp 176KB，首屏只加载当前主题那一张，可接受）、logo 296KB、**jackets 15MB**、diff 5.1MB/1185 文件。曲目库 83 个请求里有 60+ 是卡片图，已 2087/2108 懒加载，方向正确。
- CSS：Base 46.3KB（单文件含 16 套主题变量）、songs 31.5KB、auth 7.9KB、jubility 7.6KB。Base 是唯一阻塞渲染的样式表，首屏必需，暂不建议拆；若要压，可把 16 套主题的背景/装饰变量拆成按需加载的第二份。
- 第三方：`img.shields.io` 页脚徽章（已有文字兜底）、`static.cloudflareinsights.com` RUM（可关）、`cdn.jsdmirror.com`（见 2.3）。
- Service Worker：只缓存图标等静态资源、**明确不缓存 HTML 与 /api**（`public/sw.js`），策略正确，无需改。

### 2026-11-02 曲目库 1102（P0）：保留 SSR，改为两层边缘缓存 + 单飞（v1.58.0 / 提交 5252b43）

**先纠正一条测量口径**：本轮复测发现 1102 只在**缓存被绕过**时复现——
原压测脚本打的是 `/songs/?x=<纳秒>`，每个 URL 都是新 key，必然 MISS 必回源；
真实用户不带查询串、且命中缓存时，实测连打 20 次全是 `200 / x-jb-cache: HIT`。
所以准确的结论是：**1102 = 缓存未命中并发穿透**（冷 PoP、TTL 过期那一刻、被查询串击穿），
而不是「平时访问就会 503」。这一点原报告第一节写得过重，按此更正。

保留 SSR 的修法（`src/middleware.ts`）：

1. **key 只用 pathname**，忽略查询串 —— 页面内容与查询串无关（日服/国服两套 body 都是服务端一起渲染）。
2. **两层缓存**：新鲜层 300s、陈旧层 24h。新鲜层过期时**先吐旧 HTML**，再用 `ctx.waitUntil` 后台重渲一次并写回两层。
3. **单飞**：同一 isolate 内同路径的并发渲染共用一个 Promise，只跑一次。

验收（线上实测）：

| 场景 | 改造前 | 改造后 |
|---|---|---|
| `/songs/?x=…` 并发 20（缓存击穿） | 4–5 个 **503 (1102)** | **20/20 = 200 / HIT** |
| `/songs/` 并发 20（正常命中） | 全部 200（HIT） | 20/20 = 200 / HIT |
| `/songs/10000036?x=…` 并发 10（冷缓存） | — | 2 × MISS（真渲染）+ 8 × HIT，**0 失败** |

代价与红线：最多看到旧 N 秒（新鲜期 300s 内正常，过期后旧内容立即回、后台补新）；
带会话 cookie 的请求仍完全绕过缓存，绝不互串。

**SSR 语义没有任何改变**：页面仍是 `prerender = false`、仍每请求可服务最新数据（最长滞后一个新鲜期），
只是把「N 个人同时来就渲染 N 次」变成「只渲一次、其余拿现成的」。

- 新增 `src/components/GenSkeleton.astro`：等高骨架块，只画 ≤8 张占位卡 + role=status 的「加载中…」。
- `src/lib/song-view.ts` 抽出 `bySongIdAsc` 与 `groupByGen`，页面与片段端点共用同一份排序/分桶。
- 页面脚本：IntersectionObserver（rootMargin 1200px）逐块 loadFrag；`ensureAll()` 并发 3 补拉；
  `apply()` 开头加守卫——有筛选且有骨架时先补拉再算（否则命中数会漏、空态会误报）。
- 中间件缓存 key 按路径分两档：页面级只认 pathname，`/songs/frag` **必须带上查询串**（否则各世代共用 key 会串内容）。

实测（线上，390 / 1512）：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 首屏 HTML | 1,741,301 B | **417,302 B**（-76%） |
| DOM 节点 | 24,944 | **5,586** |
| 首屏卡片 | 1683 | **311**（日服 113 + 国服 198） |
| 骨架块 | — | 15 块，高度按 data-count 精确（实测 2994px / 66 首） |
| CLS（滚动 + 加载全程） | 0.03 | **0** |
| 文档高度 | 37274 | 54238（骨架按真实卡数占位，全程不变） |
| 筛选「原创」 | — | 命中 925、补拉后 1683 张卡齐 |

踩坑记录：
1. 首版骨架高度写成 0（`measureGrid()` 在带存档筛选时读不到可见卡），导致所有骨架块塌成 0 高、一进页面就全量补拉；用清空 localStorage 的干净态才复现出正确值。
2. `content-visibility: auto` 的块如果没有 contain-intrinsic-size，文档高度会塌成视口高（实测 docH 900）。
3. **同版本号内改 SSR 页面不会自动换内容**：边缘缓存 key 里带 site version，必须 bump 版本（1.59.0 → 1.59.1）才会换 key；否则陈旧层最长 24h 继续吐旧页。


### 2026-11-02 字体自托管 + 按世代预载（v1.58.1 / 提交 f68e230、2e07519）

**根因比报告里写的更糟**：不只是「第三方 CDN 多一跳」，而是 **preload 映射在 2026-10-27
换字体之后就失效了**——预载的是 jost / rye / shrikhand / playfair-700，而当时页面实际
在用的是 Montserrat / Quicksand / Raleway 等。实测首页与 /songs/ 的资源列表里能同时看到
「预载了没人用的 jost 571ms」和「真正要用的 raleway 1029–1379ms」。等于白下一次 + 慢一步。

改法：①10 个 woff2（9 款在用 + ZCOOL KuaiLe）放进 `public/assets/fonts/`；
②`theme.css` 的 `@font-face` 全改站内路径，删掉 6 条早已没人用的声明；
③`Base.astro` 预载映射从「A–G 字母」改成「世代 key → 文件名」；
④`public/_headers` 给 `/assets/fonts/*` 一年 immutable。

实测（1512×900，CDP 关缓存）：

| 页面 | 改造前 FCP | 改造后 FCP（3 次） | 字体请求 |
|---|---|---|---|
| 首页 | 2344 ms（单次） | **1140 / 1208 / 1240 ms** | 2 个跨域（含 1 个无用）→ **1 个同源** |
| 曲目库 | 4240 ms（单次） | **1952 / 2028 / 2136 ms** | 同上 |

> 口径：改造前只有单次样本，改造后 3 次；本站 FCP 方差本就大（历史出现 3 倍抖动），
> 这两个数是**量级改善的证据**，不是精确增益。更硬的结论是「字体请求从 2 个跨域
> （其中 1 个是错的）变成 1 个同源且被 preload 命中」。

**踩的坑**：`public/_headers` 注释只能用 `#`。写成 CSS 风格的 `/* */` 时 wrangler
把注释行当路径解析，报 `Expected a colon-separated header pair`——**先挂了一次 CI 构建、
又挂了一次手动部署**（线上停在 1.58.0 十几分钟）。

**顺带修掉的隐患**：陈旧层 24h 会让「部署完边缘仍吐旧 HTML」（1.58.1 上线后 /songs/ 还在
回旧 preload 的页面）。缓存 key 现在拼上 `site.json` 的 version，**每次发版 = 新命名空间**。
