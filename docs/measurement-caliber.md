# 统计口径（做任何计数前先读）

> 为什么要单独一页：2026-10-24 一晚上有 **四个人** 在同一个地方栽过 —— 数字看起来都对，
> 但数的是另一群元素，或者量的是另一种口径。这些坑不会在代码里留下痕迹，
> 只会让验收结论悄悄跑偏。放在 `docs/` 而不是塞进 `site-structure.md`，
> 是因为「口径」不是「结构」，而且这一页要能被 `grep` 直接找到。

---

## 1. 卡片数只数 `.sc-card` / `<article>`

`data-cat` 这个属性出现在 **三种** 元素上（2026-10-24 实测，v1.15.2 产物）：

| 元素 | 数量 | 说明 |
| --- | --- | --- |
| `article` | **1241** | 曲目卡，要数的就是它 |
| `button` | 7 | 分区筛选 chip（jp/cn 各一套，`all` 出现 2 次）|
| `section` | 2 | jp / cn 两个 `.sc-sec-all` 容器 |

**全页匹配 `data-cat` 会多算 9 个**（7 + 2）。只排除 `button` 仍会多算 2 个 `section`。

正确写法：

```js
document.querySelectorAll('.sc-card').length              // 浏览器
```
```js
(h.match(/<article[^>]*class="sc-card"/g) || []).length   // Node 解析 HTML
```

**禁止**：`grep -o 'data-cat="原创"' | wc -l`。

## 2. 世代块：DOM 总数 13，日服视图可见 12

- `class="sc-gen"` 块在 HTML 里共 **13 个**（jp 12 + cn 1）
- 第 13 个是「音乐魔方」，属于 **cn 服务器的 `.sc-body`**，那个容器默认 `display:none; hidden`
- 所以 **日服视图可见 12 个块**，DOM 里仍是 13

两个数都对，但**必须分开说**：「DOM 总数 13」「日服视图可见 12」。
把它们混成一个数，会得出「少渲染了一个世代」或「多出一个空块」的错误结论。

同理，卡片：**DOM 1241 = jp 1150 + cn 91**。

### 2.1 可见性维度：同一属性在两个 DOM 分支各有一份

比「DOM vs 可见」更隐蔽的一层：**同一个结构在两个分支里各渲染一份**，全页数会翻倍，但任一时刻只有一个可见。

实测（v1.15.2，`/songs/`）：

| 属性 | 全页数量 | 单视图可见 | 说明 |
| --- | --- | --- | --- |
| `h2`（世代分区标题）| **2** | **1** | jp / cn 各一个 `.sc-sec-all`，各带自己的 `h2` |
| `.sc-sec-all` | **2** | **1** | 同上 |
| `.sc-cat-set`（分区 chip 组）| **2** | **1** | jp / cn 各一套 |
| `.sc-sec-h em`（计数）| **2** | **1** | 各 body 自己的计数 |

**错误做法**：`document.querySelector('.sc-sec-all')` —— 只返回第一个（jp 那个），
于是「切到 cn 后计数还是 1150」这种**假 bug** 就会出现（2026-10-24 实测踩过）。

**正确做法**：先限定 body，再取：

```js
document.querySelector('.sc-body[data-srv="cn"] .sc-sec-all .sc-sec-h em')
```

**判据**：一个属性若在多分支结构里各有一份，**必须先声明「数全页还是数单视图」**，
否则两个数都对、但答不是同一个问题。

## 3. 压缩后的 HTML 是单行，`grep` 按行计数会翻倍

Astro/Workers 产出的 HTML 常被压成一行（v1.15.2 的 `/songs/` 页面 **1,003,715 B / 1084 行**，但卡片密集区基本在一行内）。

> **注意 B 与字符是两个量**：`1,003,715 B` 是**全文件字节数**，`877,906` 是**最长那一行的字符数**。
> 两者不是同一个数、不该相等（中文按 UTF-8 是 3 字节/字，字节数必然大于字符数）。
> 把这两个数拿去互相验证，会得出「数据不一致」的错误结论。

`grep -c` 数的是**行数**，不是匹配次数；`grep -o | wc -l` 才是次数，
但如果匹配串在同一行出现多次，仍要确认 `wc -l` 数的是每行一个还是每个匹配一个
（`grep -o` 每个匹配输出一行，通常正确，但配合其他管道容易出错）。

**统一做法**：用 Node 的 `matchAll` 或浏览器 `querySelectorAll`，不用 shell 计数。

## 4. Tab 序分视口，两个数都对

同一个 `sc-skip`，不同视口的位次不同（2026-10-24 实测）：

| 视口 | `sc-skip` 位次 | 首个曲目卡 |
| --- | --- | --- |
| 桌面 **1440×900** | 第 **9** 位 | 第 19 位 |
| 窄屏 **390×844** | 第 **6** 位 | 第 16 位 |

差异来自 header 在不同宽度下渲染的链接数量不同（宽屏有文字链，窄屏收进抽屉）。

**报告时必须带视口**。只写「第 6 位」或只写「第 9 位」，都会让另一个人以为你测错了。

## 5. 断言条数看「运行时 PASS 行数」，不是静态 `grep 'ok('`

`scripts/ci/check-song-edits.mjs`（v1.15.2）：

| 数法 | 结果 | 说明 |
| --- | --- | --- |
| 静态 `grep -c 'ok('` | **28** | 源码里写了 28 处断言调用 |
| 运行时（grep 输出行） | **39** | 实际展开执行了 39 条 |

差 11 条来自**循环展开**（`BANDS` / `CATS` 之类的表驱动断言，源码写一次、运行时展开多次）。

**计数类结论只能跑起来数输出行。** 静态数源码必错，而且错得「看起来很正常」。

另注意：`npm run check` 整链的 PASS 行数是 **42**（含 refs / song-edits / contrast 各段），
与 song-edits 单段的 39 是两个不同的数，不可混用。

## 6. 线上验证看响应头属于哪一层，不看 UA / 缓存状态

### 6.0 先说最关键的限定：**网络路径**

同一秒、同域名、同「无 UA」，**走代理与直连得到不同结果**（2026-10-24 实测各 3 次）：

| 路径 | 命令 | 结果 |
| --- | --- | --- |
| **走代理** | `curl -x http://127.0.0.1:7897 -A '' https://wiki.byd-ub.top/songs/` | **403** + `Cf-Mitigated: challenge`（3/3 一致）|
| **直连** | `env -u ALL_PROXY -u HTTPS_PROXY curl -A '' https://wiki.byd-ub.top/songs/` | **307** → `https://wiki-cn.byd-ub.top/songs/`（3 次里 2 次，1 次连接失败）|

**成因**：走代理时出口是海外 IP（SIN/HKG），CF 对「海外 IP + 无 UA + 高频」更易触发机器人挑战；
直连是本地 IP，先命中域名跳转规则。**差异在出口 IP 与规则匹配顺序，不在 CF 策略变化。**

> **所以本节所有结论都必须带「在什么网络路径下测的」。**
> 少了这句，别人用另一条路径复现不出来，就会推翻整节。

### 6.1 链路是三层叠加，不是二选一

实测 `wiki-cn.byd-ub.top/songs/` 的一个 200 响应里**同时**带两家的头：

```
Server: cloudflare
CF-RAY: a4f70391499de10e-IAD          ← Cloudflare 层在场
Age: 232
EO-LOG-UUID: 10337981676968411963      ← EdgeOne 层也在场
EO-Cache-Status: HIT
```

链路：**用户 → Cloudflare → EdgeOne → Workers**

| 层 | 特征响应头 | 非 200 表现 | 判据 |
| --- | --- | --- | --- |
| **Cloudflare** | `Server: cloudflare`、`CF-RAY` | 307 跳 wiki-cn（域名规则）/ 403（机器人挑战）| 有 `Location`=跳转；有 `Cf-Mitigated`=挑战 |
| **EdgeOne** | `EO-Cache-Status`、`EO-LOG-UUID` | 缓存命中时返回 `Age>0` 的旧响应 | 有 `EO-*` 说明经过了这一跳 |
| **Workers** | `Cache-Control`、`Content-Type` | 500/501 才是站点真故障 | 既无 `CF-*` 也无 `EO-*` |

### 6.2 三种非 200 与各自判据

1. **307 跳转**（直连 + `wiki.byd-ub.top` → `wiki-cn.byd-ub.top`，CF 域名规则）
   判据：响应头有 `Location`。`curl` 加 `-L` 跟随即可，**不是故障**。

2. **403 + Cf-Mitigated: challenge**（**走代理 + UA 不像真实浏览器** 时稳定触发）
   触发条件：`curl -x <proxy>` + UA 不是完整浏览器指纹（海外出口 IP 更易被判机器）。
   本例实测：走代理 7897（SIN/HKG 节点）7 样本全 403；不走代理得 307。
   **关键细节：被检查的不是「有没有 UA 字段」，而是「像不像完整浏览器」**（各 8 样本重复验证，稳定）：

   | 走代理时的 UA | 结果 |
   |---|---|
   | 无 UA（curl 默认 `curl/8.x`） | **403** ×8 |
   | `Mozilla/5.0`（简短，像爬虫） | **403** ×8 |
   | `Mozilla/5.0 (compatible; Googlebot/2.1)` | **403** |
   | 完整 Chrome：`Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/131.0.0.0 Safari/537.36` | **200** ×8 |

   所以「随手加个 UA」不够，要加**完整的浏览器 UA 串**。
   判据：响应头有 `Cf-Mitigated`。

3. **EdgeOne 缓存命中**（`wiki-cn` 域，响应头同时有 `CF-RAY` 与 `EO-Cache-Status`）
   判据：有 `EO-*` 头，且 `Age > 0`。

### 6.3 不要写进口径文档的三句话

| 不要写 | 为什么 |
| `必须带 UA 否则 403` | 实测缓存命中时无 UA 也是 200 —— 会被下次缓存 HIT 打脸 |
| `缓存未命中导致 403` | 实测过一条 cache MISS 也是 200，归因不成立 |
| `CF 策略十分钟变了一次` | 真相是代理 vs 直连走了不同路径；**写成因会被打脸，写判据不会** |

**总纲：判据永远是看响应头属于哪一层 —— `Location`=跳转、`Cf-Mitigated`=挑战、`EO-*`=EdgeOne。**

## 一句话总结

**报任何数字时，同时说明：①这个数在数什么 ②用什么方法数的 ③在什么条件下量的。
并列出现多个数字时，每个都要单独标注归属，不能靠顺序暗示。**

## 两条元规则（比上面五条更通用）

### 元规则 1：写自检时，问「每个数字都在验证范围内吗」

只写「这个数要看运行时」而不真跑一次，等于**没验**。
本页第 5 条一开始就是这样：脚本里只有一句注释「需跑脚本，这里只标注方法」，
数字（28 / 39）却不在任何断言里。补法是把「标注」改成「真跑」。

> 自查动作：写完自检脚本后，逐条比对「文档里的数字」与「脚本里的断言」——
> 有数字没断言，就是漏的。

### 元规则 2：能用关系断言，就别用数字断言

本页第 5 条的最后那条断言是：

```js
add('运行时 > 静态（循环展开导致差额）', runtimeOk > staticOk, true);
```

它验的**不是** 39 和 28 这两个具体数字，而是「**运行时数 > 静态数**」这个**关系**。

好处：将来断言从 39 涨到 45、静态从 28 涨到 32，这条断言**照样通过** ——
因为它守的是「循环展开确实存在」这个**不变量**，而不是某个时刻的数值。

同理，第 2 条的「DOM 13 / 可见 12」也该优先验关系（可见 < DOM，差额 = cn 的块数），
绝对值只是当前快照。

**数字会变，关系不会。** 能写成关系的，就不要写成数字。

## 附：本页数字如何自检

本页不是抄来的，是量出来的。想验证或确认产物有没有变化，跑：

```bash
# 1) 取一份当前产物快照
curl -s -A 'Mozilla/5.0 Chrome/131' http://127.0.0.1:8787/songs/ -o tmp/songs-snapshot.html
# 2) 复算本页引用的数字
node tmp/verify-caliber.mjs tmp/songs-snapshot.html
```

脚本逐条比对 12 项（v1.15.2 实测 10 PASS + 2 INFO），包括：

- `data-cat` 在三类元素上的分布（article / button / section）
- 卡片数与世代块数
- **最长行长度 877,906 字符** —— 这就是为什么 `grep -c` 在这里必然数不准：整片卡片区压在同一行里
- **断言数**：静态 `grep 'ok('` = 28 vs 运行时 PASS 行数 = 39（脚本会真跑一次 check-song-edits）

> **脚本不需要跑站点实例**：它读的是 HTML 快照文件 + 本地源码，
> 所以在实例停着、或只有线上快照时都能验。
>
> **INFO 项不是「对错」**：最长行 > 100KB、总行数 < 2000 这两条是**解释性事实**，
> 只用来佐证 grep 陷阱成立，不设 PASS/FAIL —— 否则读者会误以为「行数少就是对的」。

**若脚本报 FAIL，先判断是文档过期还是产物结构变了**：
- 产物结构变了（例如 `data-cat` 又加到了新元素上）→ 更新本页
- 只是页面内容变了（曲目增减）→ 卡片数那几行按新版更新，口径不变
