## 先说结论

这个站的后端底子比绝大多数个人项目扎实：密码用 PBKDF2 + 每用户盐、会话只存 token 的 SHA-256、改密踢全部会话、登录用固定假 hash 抹平时序、回跳只认站内相对路径、高权限动作一律在服务端复核 role。注释里还逐条写了「为什么这么做」和踩过的坑（`middleware.ts:49-53` 那段是真实事故复盘）。

问题集中在三块：**边缘体验与缓存口径**（登录用户完全没缓存、/jubility 漏出白名单）、**时区口径分裂**（运势种子仍是 UTC，热榜已改 +8）、**长期维护成本**（浅色主题名硬编码 105 处、零 CI、683MB 的 archive 躺在仓库里）。

下面按严重度排，不按模块分。

---

## 严重

### 1. 运势种子用 UTC，热榜用 +08:00，凌晨八小时互相错位
- 位置：`src/components/Fortune.astro:27` vs `src/lib/hot.ts:15,24`
- 证据：
  - `Fortune.astro:27` — `const seed = new Date().toISOString().slice(0, 10);`
  - `hot.ts:15` — `const TZ_OFFSET = 8 * 3600000;   // 北京时间固定 +08:00，无夏令时`
  - `hot.ts:24` — `return new Date(ts + TZ_OFFSET).toISOString().slice(0, 10);`
- 影响：北京时间 00:00–08:00 这八小时，运势种子算的是「昨天」，而热榜快照读取用的是「今天」。首页左栏给人昨天的运势、右栏是今天刚封的榜。`hot.ts:22-23` 的注释记着 2026-11-03 16:50 就实撞过一次同类错位（`dayOf()` 返回 11-04，页面去读一个不存在的快照），修了 hot 一侧，运势这侧没跟着改。
- 建议：把种子改成 `dayOf()`，直接 import 现成的。种子是纯展示用，不需要另外一套口径。

### 2. `/jubility` 不在缓存白名单，却每次都全量 SSR
- 位置：`src/middleware.ts:136` vs `wrangler.jsonc:65`（顺带 `middleware.ts:128,130` 的注释也已滞后）
- 证据：`middleware.ts:136` 的 `const PUBLIC_CACHE = /^\/($|songs(\/|$)|recent(\/|$))/.test(url.pathname);` 只放 `/`、`/songs/`、`/recent/`；`wrangler.jsonc:62-65` 却已经把 `/jubility` 写进 `run_worker_first`，并在注释里写明「和 /songs/ 一样要在运行时读 D1 现算」。顺带一提，`middleware.ts:130` 的红线注释还停在旧版「只放 /songs/ 与 /recent/」，连紧邻的 :132-135 给 `/` 开的白名单都没同步。
- 影响：`jubility.astro:30` 每个请求都 `getAllSongs()` 拉全曲库（1248 行 × 16 列），再按 `jubility.ts:139-205` 给两服各算一遍理论值、上位 30、档位分布。这是全站最贵的一个页面，等于冷启动成本乘以每次访问量，而换到新曲时页面本来也允许有 FRESH_TTL 级别的延迟。`wrangler.jsonc:62-64` 的注释解释了「为什么必须走 Worker」，`middleware.ts` 这边却没有任何一句解释为什么它进不了白名单——两处口径各写一半。
- 建议：正则补 `jubility`。若担心「新曲上线理论值要立刻变」，把 FRESH_TTL 调小对该路径单独生效即可，别整个跳过缓存。

## 高

### 3. 登录用户完全不走缓存，连公共页也每次回源
- 位置：`src/middleware.ts:137,140`
- 证据：`const hasSession = !!token;` → `if (!PUBLIC_CACHE || hasSession || !isRead) return next();`
- 影响：一个登录用户访问 `/songs/`，每次都要重渲那一屏。而 `/songs/` 页面对登录与游客的 body 确实**完全一样**——`songs.astro` 全文没有一处 `Astro.locals`（grep 命中 0；全站页面层只有 account/admin/login/register 四个页面读 locals），登录态是客户端在 `me.ts:3-6` 注释说明的那套流程里事后补的顶栏。现在的逻辑是把「个性化」当成「私有」，用最贵的方式买了一个并不存在的正确性。
- 建议：把 `hasSession` 从「整段跳过」降级为「只在需要登录态的路径上跳过」。`/songs/`、`/recent/`、`/songs/frag` 三个路径按纯公共处理，不判 cookie。

### 4. 后台编辑页把 `alt` 当「长押谱」，与 schema 和三处前端相反
- 位置：`src/pages/admin/songs/[songId].astro:105,114`
- 证据：
  - :105 — `<dt>长押谱</dt><dd>{song.alt ? '是（标题带 [ 2 ]）' : '否'}</dd>`
  - :114 — 提示「长押谱的标题末尾带 [ 2 ]」
  - 反方：`db/schema.sql:25` — `alt INTEGER ... -- 1 = 该行是 [ 2 ] 谱面（标题带 [ 2 ]）。**不代表有长押**，见 has_hold`；`src/lib/db.ts:46-60` 注释「与 alt 无关，alt=1 只表示 [ 2 ] 谱面（主人 2026-10-31 纠正）」；`SongCard.astro:54-55` 同口径
- 影响：维护者打开编辑页，读到的是「这一栏叫长押谱」，会被引导去按 [ 2 ] 判断长押。而真实字段是 `has_hold`（三态 1/0/NULL，`schema.sql:30` 明确「不要用 0 冒充未知」），编辑页压根没显示它。
- 建议：编辑页把 `alt` 标成「[ 2 ] 谱面」，另起一行显示 `has_hold` 的三态（是 / 否 / 未知，主人已定此文案）。全站「长押」74 处里，`songs.css:603` 还在写「右上角是 [2] 长押谱徽章」，而同文件 `:1070-1071` 已经写明「不代表有长押」——同一个文件自己跟自己打架。

### 5. 登录 / 注册 / 改密三个端点都没有任何限流
- 位置：`src/pages/api/auth/login.ts:24-91`、`register.ts:36-99`、`account/password.ts:27-77`
- 证据：三个文件 grep `rate|limit|Map<` 全部无命中。登录有 Turnstile（:41），改密**连 Turnstile 都没有**，只要带着一个有效会话就能刷。
- 影响：PBKDF2 100_000 次迭代是故意慢的。`auth.ts:12-20` 注释解释过免费 Workers 的 CPU 预算撑不住更高（OWASP 建议 600k，这里取 100k 并写明「出现 1102 就下调」），于是每个登录请求本身就是一笔可观的 CPU 支出。Turnstile 挡的是自动机，挡不住「人已经过了验证、然后循环打 500 次」。改密端点更是裸的。
- 建议：站内已有现成范式——`hot/hit.ts:36-43` 的 `bump()` 用 KV 计数器 + 上限 + TTL，直接抄一份到 auth 侧（按 IP 每分钟 10 次足够）。KV 读-改-写在并发下是近似的，但挡洪峰本来就是它的用途，`hit.ts:35` 注释已经把这点交代清楚。

## 中

### 6. 全站零安全响应头
- 位置：全站无 `_headers` 文件，`wrangler.jsonc` 无 `headers` 段；grep `Content-Security-Policy|X-Frame-Options|Referrer-Policy|X-Content-Type-Options|Permissions-Policy|Strict-Transport` 在 `src/` 下 0 命中。
- 影响：缺 CSP（页面靠 `is:inline` 脚本跑，一处逃逸就直通），缺 `X-Content-Type-Options: nosniff`，缺 `Referrer-Policy`（页脚有 shields.io 与 GitHub 外链，`Base.astro:224-225`）。
- 建议：现实起点是「加三个不需要改代码的头」——`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`X-Frame-Options: SAMEORIGIN`。CSP 另开工单：站内 `<script is:inline>` 有 20+ 处、还有 Turnstile 从 `challenges.cloudflare.com` 拉脚本（`Turnstile.astro:60`），直接上 `script-src 'self'` 会白屏，得先走 `Content-Security-Policy-Report-Only` 攒一段真实违规。

### 7. 每次缓存命中都整份复制 HTML
- 位置：`src/middleware.ts:34,41,58,77`
- 证据：快照的 body 类型就是 `ArrayBuffer`（`:34`），`snapshotOf` 用 `await res.arrayBuffer()` 整份读进内存（`:41`）。之后每一次使用都 `slice(0)` 复制一份：`:58` 的 `respondWith`、`:77` 的 `putBoth`（fresh / stale 各复制一次）。一次 fresh 命中 = 复制 3 份，一次 STALE 命中 = 复制 1 份。
- 影响：`ArrayBuffer` 不能跨 Response 共用是对的，但这意味着每次「缓存命中」都要付一遍整站最大页面的 memcpy。`/songs/` 自 2026-11-02 起已分段加载（首屏 100–220 首，HTML 从 1.74MB 降到约 250KB，`songs.astro:212-217`），`/jubility` 仍是全量 SSR 的大页。前者在白名单里、后者该在白名单里，这一条改完是两个路径一起受益。
- 建议：把缓存的 body 换成 `ReadableStream`，用 `tee()` 分给各个使用方（`cache.put` 收流是支持的）；退一步也可以只在 `putBoth` 里 tee 一次，省掉两次写缓存的复制。

### 8. 首页每次请求跑一次全表 SUM
- 位置：`src/components/Fortune.astro:34,36`
- 证据：`:34` 的 `COUNT_SQL` 对 `songs` 全表做两次 `SUM(CASE WHEN server_x = 1 ...)`，`:36` 每个请求执行一次，无缓存。
- 影响：结果几乎恒定（只在发曲时变），却每次首页都扫一遍全表。`db.ts:79` 的 `TTL_MS = 60_000` 缓存（`:115`）只覆盖 `getAllSongs`，不覆盖这条。
- 建议：扔进 `getAllSongs` 的同一次取数里算，或干脆在 build 期把两服计数写进 `site.json`。

### 9. `cacheFullInBackground` 把整份音频读进内存
- 位置：`src/pages/api/audio/[songId].ts:296-311`
- 证据：`:298` 重新 fetch 一份、`:301` 的 `const buf = await up.arrayBuffer();` 把整份读进内存、`:302-307` 再塞 `cache.put`。
- 影响：一首 jubeat 曲 2–5MB，整份落内存再写缓存。Worker 内存上限内能过，但并发几路就是几 MB 乘几倍。
- 注意：`:293-294` 的注释是有理由的——「必须等响应交出去之后跑（waitUntil），不能用当前响应的流，也不能是 ReadableStream body —— 两者都会拖慢首字节或直接写不进去」。所以不能简单把响应那支流复用过来，得是独立的一份。
- 建议：`cache.put` 收 ReadableStream 是支持的（上面「写不进去」的老经验值得重测一次，多半是当时把带 `content-length` 的响应拼错了）。若测得通，改成 `up.body.tee()` 一支给 `cache.put`、一支丢弃，内存占用就与曲长脱钩；若仍不行，退一步按 `content-length` 设阈值，超 3MB 就干脆跳过缓存。

### 10. 浅色主题名硬编码 105 处
- 位置：`theme.css` 76、`jubility.css` 18、`fortune.css` 6、`songs.css` 4、`server-card.css` 1
- 证据：`server-card.css:95` 是最典型的形态——`html:not([data-g="knit"]):not([data-g="prop"]):not([data-g="qubell"]):not([data-g="ripples"]):not([data-g="saucer"]):not([data-g="yymf"]) .sc-line { filter: invert(1); }`
- 影响：加一套浅色主题要回头改六处；漏一处就是「新主题下某块图反色了/没反」。`theme.css:1908,1935,1958,1987,2045,2073` 六套浅色各自写了 `color-scheme: light`，但没有任何画面层拿它当判据。
- 建议：在 `:root` 上把 `color-scheme` 暴露成自定义属性，或直接在 `Base.astro` 输出 `data-lum`，CSS 侧统一按 `[data-lum="light"]` 写。这是纯机械改造，改完能把这 105 行压到个位数。

### 11. 首页主题数写死 15，实际是 16，且这个数会进 meta description
- 位置：`index.astro:13`（`const THEME_COUNT = 15;`）vs `ThemeScript.astro:10-27`（`GEN` 数组 16 条）vs `lib/gens.ts:19-33`（13 世代）
- 证据：
  - `index.astro:10-12` 整段注释在自证清白，但三句里错两句：「15 个世代 → 15 套主题」（`GEN_ORDER` 实为 13）、「14 条可切换 + 音乐魔方 = 15」（既漏数 `saucerfulfill`、又把 `clan` 的 1 个世代当 4 个算，14 这个数本身还对不上 13），最后一句「实测 ThemeScript 的 GEN 数组就是 15 条」是硬结论——实际 16 条（`ThemeScript.astro:11-26`）。
- 影响：注释自己说「别再把这两个数写成打架的两个值」，结果第三个值又写错了，还错进了 SEO 描述。三处各写一份、谁都不读谁，改主题必漏。

### 12. 热榜不足 25 名时用「最近上架」补位，展示上与真上榜无法区分
- 位置：`src/components/HotBoard.astro:41-52`（补位在 `:43` 取 `fallbackPool(db, TOP)`）
- 证据：`:50` 补位条目写死 `rank: list.length + 1, delta: 0, isNew: false`。`delta: 0` 在界面上落到 `:83` 的 `fh-flat` 分支，即三根 `opacity: 0.4` 的暗柱（`fortune.css:414`）；`isNew: false` 则直接跳过 `:80` 的「新」徽章分支。文字版「名次不变」只在 `:89` 的 `.fh-sr` 里，`fortune.css:451-458` 是 `clip-path: inset(50%)` 的读屏隐藏——视觉上看不到这三个字，看到的只是三根暗柱。
- 建议：补位条目另给一个标记（`filled: true`），行尾显示「新上架」或直接留白；或者干脆减少补位数量，让「不足 25」这件事在视觉上成立。
- 影响：`:38-40` 的注释把它当设计选择（「真热度涨上来后这一段自然会被挤掉，不需要什么时候回头删」），所以现在线上大概率长期处于「不足 25」，榜里大半是补位而来的新曲，读者看起来和真热度完全一样——真上榜且名次确实没变的那一行，视觉上也正好是同一组暗柱。`isNew` 那栏还更讽刺：补位池 `fallbackPool` 取的正是「最近上架」（`:43`），本该最像新曲，却被硬写成 `false`，于是既没「新」徽章、也没上升势头。

### 18. 零 CI，且没有 lint / typecheck / test

## 做得好的地方（建议保持）

- `src/lib/auth.ts:1-22`：三段头注释分别解释「不存明文」「PBKDF2 迭代为何取 100k」「免费 Workers 的 CPU 预算」，还写了「以后要提强度只改 PBKDF2_ITER，老用户在下次登录成功时自动重算升级」——这条升级路径是真的实现了（`verifyPassword` 返回 `needsRehash`，`login.ts:63-69` 消费它）。
- `login.ts:51-56`：用户不存在时用一个固定假 hash 跑满一次校验，抹平时序，防邮箱枚举。
- `login.ts:79-82`：回跳只认 `/^\\/(?!\\/)/`，注释点名「不做这层校验就是开放重定向漏洞」。
- `password.ts:61-64`：改密后 `DELETE FROM sessions` 再给当前设备发新 token，注释说明是防「cookie 被盗后直接改密锁人」。
- `song-admin-server.ts`：把写入口抽成不依赖 Astro 的纯函数，`readForm` 用 lambda 懒传，越权请求连请求体都不解析（`:63-64` 注释「大包 DoS」）。这是全站可测性最好的一个模块。
- `db/schema.sql`：几乎每张表每条关键列都写着决策来源与日期（`:25` 的 alt 澄清、`:29` 的「不要用 0 冒充未知」、`:65-69` 的四级身份模型）。
- `middleware.ts:111-130`：三条缓存红线和 2026-11-02 的事故复盘写在同一处，包括「绝不把带 Set-Cookie 的响应写进缓存」。
- `hot/hit.ts:6-12`：四层防刷按重要性排序，第一层直接落在表主键上而不是应用层。
- 全站 `!important` 只有 4 处。
